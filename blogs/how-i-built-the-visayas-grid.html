How I Built an Interactive Model of the Visayas Power Grid

A public map of an island power system, built from imperfect data, engineering judgment, and a deliberately simple architecture.

Most people only notice the power grid when it stops working. Behind every light switch is a network of generators, substations, transmission lines, and control systems balancing electricity from one moment to the next.

The Visayas makes that network especially interesting. Its major load centers and power plants are spread across several islands. Cebu, Negros, Panay, Leyte, Samar, Bohol, and nearby islands are tied together by overhead lines and submarine connections. The region also exchanges power with the wider Philippine grid.

I wanted to make that system easier to see. So I built VisayasGrid: an interactive map and offline power-flow model of the Visayas transmission network.

What I was trying to build

The goal was not to recreate an electric utility's control room. I do not have access to NGCP's private network model or real-time operating data. The goal was smaller and more useful: build a public, inspectable model that shows how the main Visayas transmission network fits together and how power might move through it under a defined set of assumptions.

The current dataset contains 54 buses, 60 lines, 7 submarine connections, and 115 generator units. In power-system language, a bus is an electrical connection point—usually a substation or part of one—where lines, loads, and generators meet. It is not a passenger bus, although that misunderstanding has made the project harder to explain than the load flow itself.

The map lets you filter the network by island and voltage, search for substations, inspect buses and lines, and compare several demand scenarios. It turns a collection of tables and engineering parameters into something you can explore.

The difficult part was the data

A map needs coordinates and connections. A power-flow model needs much more: voltage levels, line impedances, load estimates, generator capacities, and a reference point for the entire network.

There is no single public file containing all of that for the Visayas Grid. I started with PyPSA-PH, an open model of the Philippine power system, then checked and corrected the Visayas subset using public material from NGCP, DOE plant lists, OpenStreetMap, OpenInfraMap, and other available records.

Some fields can be sourced directly. A substation's existence, approximate location, voltage level, or the connection between two areas may appear in public documents. Other fields are not published. Line impedance and demand at an individual bus, for example, often require a documented engineering estimate.

I did not want those two categories to blur together. The project keeps a source ledger that labels values as sourced, inherited from PyPSA-PH, or an estimate. That distinction matters because a model can look precise while resting on uncertain inputs.

A converged model is not automatically a correct model. It only proves that the equations found an answer for the assumptions I gave them.

How the model works

The project has two separate halves. Python prepares and solves the electrical network. The website displays the finished result.

Public data + engineering assumptions
        ↓
Clean buses, lines, generators, and scenarios
        ↓
pandapower load-flow calculation
        ↓
GeoJSON files
        ↓
React + Leaflet interactive map

The Python pipeline first turns the raw records into clean tables. It assigns readable names, joins generators and loads to the correct buses, handles different voltage levels, checks which parts of the network are connected, and creates demand and generation scenarios.

It then builds the electrical network in pandapower, a Python library for power-system analysis. The program runs a load flow: a calculation that estimates the voltage at each bus and the real and reactive power moving through each line.

In simple terms, the solver checks whether the selected generation and demand can be balanced through the network I described. One bus at Ormoc acts as the reference, or slack bus. It absorbs the remaining mismatch and serves as a proxy for power exchanged through the HVDC connection. Transformers handle connections between buses at different voltage levels.

The default result requests an AC load flow for the peak-demand scenario. AC is the more complete representation because it considers voltage magnitude, reactive power, and losses. If that calculation cannot converge, the build can fall back to a simpler DC approximation, and the output records which solver actually succeeded. The app also includes mean-demand, off-peak, and separate DC datasets.

Why the website has no backend

My first design was much heavier. It included a database, an API, containers, and a cloud server. It was a reasonable architecture for a large platform, but unnecessary for a small network that changes infrequently.

So I removed almost all of it.

The load flow runs offline. The results are exported as GeoJSON and committed with the website. React manages the filters and panels, while Leaflet draws the buses and lines over a basemap. Vercel serves the finished files. There is no runtime database, API server, user account, or browser-side power-flow solver.

This made the project cheaper to host and easier to maintain. More importantly, it let me focus on the part that mattered: the network model and the way people explore it.

How to read the map

Each marker represents a modeled electrical bus. Each line represents a transmission connection between two endpoints. Colors separate the main voltage levels—69, 138, 230, and 350 kV—and the interface can also show line loading from the selected solution.

You can click a feature to inspect its properties, filter the view by island or voltage, search for a substation, and switch between available scenarios. Selecting a bus highlights its immediate neighbors so you can follow the local network without losing the larger picture.

The lines on the map are straight connections between substations. They do not reproduce the surveyed route of every transmission tower or submarine cable. The visual is about electrical topology—what connects to what—more than exact right-of-way geometry.

What the model cannot tell you

VisayasGrid is not live telemetry. It does not show today's dispatch, current outages, actual bus voltages, or the real loading of NGCP equipment. The build date tells you when I generated the files, not when the grid conditions were observed.

The scenarios combine historical demand patterns with estimated dispatch. Some circuits are aggregated into a single map feature. Generator units are grouped at their connected buses. The HVDC interchange is represented by the slack-bus result rather than a fully controlled and capacity-constrained link.

These limits do not make the model useless. They define the questions it can answer. It is good for understanding the network's structure, learning how a power-flow pipeline works, and exploring the consequences of stated assumptions. It is not suitable for operating decisions.

What I learned

The frontend was not the heart of this project. The hard work was deciding what the data meant, checking whether connections were physically sensible, handling mixed voltage levels correctly, and refusing to treat a plausible result as proof.

I also learned that a smaller architecture can produce a stronger project. Removing the backend did not reduce the engineering value. It made the system easier to understand. The complete path—from source record to solved value to visible feature—can be inspected without chasing requests across several services.

That is the part of the project I care about most: not just producing a map, but making the reasoning behind it visible.

What comes next

The main transmission backbone is already modeled, but the network is not complete. The next phase is to expand the 69 kV sub-transmission layer, beginning with missing load-end substations and unresolved locations. After that, I plan to connect more DOE-listed generators and reconcile the network against additional one-line diagrams and public records.

The method will stay the same: source first, estimate only when necessary, label the difference, rebuild the model, and check the result before publishing it.
